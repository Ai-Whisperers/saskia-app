## Overview

[DORA](https://dora.dev) (DevOps Research and Assessment, now at Google Cloud) tracks 4 metrics that together describe the performance of a software delivery organization:

1. **Deployment Frequency** — how often you ship to production
2. **Lead Time for Changes** — from first commit to running in production
3. **Change Failure Rate** — % of deploys that cause a rollback or incident
4. **Mean Time to Recovery (MTTR)** — how fast you recover from a bad deploy

The 2026-10-09 CI recovery (PR #88) moved Sazon from "Low" to "Medium" in 24 hours. This document is the quarterly dashboard to track whether we hold that improvement.

## Data sources

All four metrics are derived from data that already exists in GitHub + the VPS. No new instrumentation needed beyond `scripts/dora_snapshot.py` (planned).

| Metric | Source | API / Command |
|---|---|---|
| **Deployment Frequency** | `gh api repos/Ai-Whisperers/saskia-app/deployments` | list of deployment events; or count distinct `vYYYY.MM.patch` tags pushed per week |
| **Lead Time for Changes** | `gh pr list --state merged --json createdAt,mergedAt,number` | (mergedAt − createdAt) is PR-cycle time; lead time also includes the deploy lag, which is the time from `merge` to the first deployment SHA matching the merge SHA in `docker service inspect saskia-vps_web` |
| **Change Failure Rate** | count of `git revert` / `git reset` to main in the 24h after each prod deploy + manual incident log | `gh api repos/Ai-Whisperers/saskia-app/commits?since=<deploy_sha+24h>` and grep for revert/rollback keywords; plus a simple incident log at `docs/operations/incidents/2026-Q4.md` |
| **Mean Time to Recovery (MTTR)** | first "bad deploy" detection → `sazon rollback` completion | the rollback script emits a `migration_rollback_log:<ts>` row in `app_meta` (per SASKIA-209); compare to the bad-deploy timestamp |

## Baseline (pre-2026-10-09, before PR #88)

| Metric | Value | Comment |
|---|---|---|
| Deployment Frequency | ~1/week (manual) | Operator ran `./scripts/deploy.sh --env=prod` by hand; prod went 0-2 times per week depending on perceived urgency |
| Lead Time for Changes | 2-3 days (median) | PR opens, days-long review queue, manual prod deploy after merge |
| Change Failure Rate | ~40% (estimate) | 5/11 CI workflows were always red; fix-by-pushing-to-main was the norm; every push was effectively a "did this break" check |
| MTTR | 6-12 hours | No automated rollback; next-day fix-by-pushing-to-main |

**DORA bucket:** Low. (Elite / High / Medium / Low — Google's 2024 benchmarks).

## Targets for 2026-Q4 (Oct-Dec)

| Metric | Target | Why |
|---|---|---|
| **Deployment Frequency** | 1/day to dev, 1/week to test, 2-3/week to prod | Dev auto-deploys on every push (deploy-dev.yml); test on every PR + merge; prod via CalVer tag |
| **Lead Time for Changes** | <4 hours (PR → test deploy); <24 hours (PR → prod) | Auto-deploy-test on PR open + sync removes the manual deploy step |
| **Change Failure Rate** | <15% | The dev-ci gate (PR #88) catches lint + format + route-smoke before deploy-dev; only 1 in 7 pushes should reach prod with a real bug |
| **MTTR** | <1 hour | `sazon rollback [--to N] [--dry-run]` (SASKIA-209) provides one-command rollback; from detection to recovery should be <60 min |

**DORA bucket at target:** High. (Elite is unreachable with one dev; High is realistic for a small AIW-style team.)

## Appendix B: 4 metric definitions (operational)

- **Deployment Frequency** — count of successful production deploys per time period. A "deploy" is a `docker service update` on the `saskia-vps_web` service that results in a running container. Rollbacks count as a deploy; reverted reverts don't.
- **Lead Time for Changes** — `first commit on the PR's branch` to `prod deploy SHA matches the merge SHA`. Excludes PRs that never reach prod. Median over the period.
- **Change Failure Rate** — count of deploys that result in a rollback OR a `revert:` commit in the next 24h, divided by total deploys.
- **MTTR** — time from the first user-visible impact of a bad deploy (e.g., a 5xx spike, a missing feature, a customer report) to the resolution (rollback complete, fix shipped, or the next good deploy).
